# Plan: #14 Preserve transcript sessions and tolerate unavailable browser storage

## Files that change

- `client/src/App.tsx`: give utterances stable identities and captured session/settings ownership; ignore cancelled operation callbacks and start completions; save only pending final utterances and mark successful saves.
- `client/src/types.ts`: carry utterance/session identity and captured target languages.

- `client/src/components/History.tsx`: use validated history loading and safe deletion without changing styling.
- `tests/transcript-persistence.test.ts` and `tests/settings-storage.test.ts`: behavioural regressions covering App wiring, repeated utterances, session boundaries, write retries, storage corruption, and cancelled recording starts.

## Risks

- A failed browser storage write must keep final utterances pending so a later save can retry.
- An old controller may finish starting or invoke callbacks after cancellation: invalidate its operation before stopping and capture the controller/session locally.
- Repeated text is legitimate: deduplicate only by utterance identity inside its session.
- Browser storage may contain invalid JSON or wrong-shaped records: filter invalid data and continue in memory if the storage API throws.
- Keep the existing JSX styling and all provider/API contracts unchanged.
