## Exact shared contract

All environment fields are optional/default off: `ACCOUNTS_ENABLED` operates only at exact `1`; `IDENTITY_SERVICE`, `IDENTITY_CALLER_ID`, `IDENTITY_CALLER_SECRET`, `ACCOUNT_DB`, `ACCOUNT_ENVIRONMENT` (`production`/`preview`), canonical HTTPS `ACCOUNT_ORIGIN`, and distinct reverse `IDENTITY_ERASER_CALLER` / `IDENTITY_ERASER_SECRET`. No binding IDs or enabled switch are invented.

Reuse the reviewed immutable private `eugnel-platform/auth` `createIdentityClient({binding,callerId,secret})`, with its five-second bounded, no-retry HMAC transport. Request `/v1/session` with only `{token}` from exactly one `__Host-eugnel_session` cookie. Require returned `{scope:{productId:'rtt',environment,origin},session:null|{accountId,authenticatedAt,expiresAt}}` to match fixed trusted configuration, validate bounded opaque ID/timestamps, and freeze the verified principal. Browser account headers, JSON account IDs, desired scope and forwarded origin cannot establish authority. Malformed/ambiguous cookies refuse. Missing enabled configuration returns static 503; signed-out/expired returns 401; neither falls back to owner KV.

Reverse erasure uses the shared `createServiceAuthenticator`, fixed action `erase`, role `eraser` and only the configured reverse caller/secret with fixed RTT environment/origin. POST `/_internal/identity/erase` accepts only signed `{accountId,jobId}` after replay/scope/principal checks and acknowledges `{ok:true,jobId}` after the transaction. A product sign-in caller cannot erase. Fresh signed same-job retries are idempotent; replayed nonces refuse. It is not a public account-ID-taking `/api` endpoint. Shared identity fences/revokes first and removes identity only after this eraser acknowledges. API agent will export/decorate these reviewed transport APIs and exact action in the final package; no transport core is copied into public RTT.

## Security review points and limits

The risky decisions are fixed scope/server authority, cookie ambiguity, reverse HMAC principal separation, transaction result validation and permanent commit fencing. Review these explicitly before implementation. D1 accounts never imply shared provider credentials, browser cache erasure or cross-domain SSO. A request that already read data before deletion cannot retract an in-memory/provider copy; newly committed profile writes and reads after a fence must refuse. Disabled-mode rollback is for the existing owner-only deployment, not a way to re-enable access for previously enabled customer callers. Actual service/product D1 bindings, reviewed migration receipts, trusted registry/credentials, Access-compatible callbacks, retention facts and two-account live proof remain activation dependencies owned by the full #8 delivery. Do not mark the baseline done from this server slice alone.
