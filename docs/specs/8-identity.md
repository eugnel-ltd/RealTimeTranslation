# Full shared D1 identity and RTT accounts

Status: independently APPROVED by the root orchestrator on 18 October 2026 before source implementation. Root confirmed separate product D1, captured registry/HMAC/nonce, central quota authority, durable identity-last deletion and scoped browser storage. This completes the implementable service and consumer flows; it is not another session-foundation deliverable.

## Decisions and boundaries

- The owner chose one shared Cloudflare D1/Workers identity implementation, reusing Word Camp spec 61; Supabase is rejected. Preserve every legacy platform export and existing canonical account ID.
- Continue platform PR43's `createD1SessionStore` and hash-only scoped sessions. Verified Word Camp source is `85aab34699a231244c2c63695b421a21e111b17b`, auth modules/routes and migrations `0004_accounts.sql`/`0005_auth_flow_used.sql`.
- Identity D1 owns accounts, proofs, sessions, linking and deletion coordination. Customer profile data uses a separate RTT product D1, approved by the orchestrator on 18 October. Existing owner-only global KV profiles remain untouched. No implicit transfer of their ownership or browser history occurs.
- Only the exact server flag `ACCOUNTS_ENABLED=1` operates. Missing required bindings, registry or credentials fails closed with static unavailable errors; it never falls back to global owner profiles. Default configuration is off. No resource, binding ID, credential, provider registration, quota allocation or deployed origin is fabricated.
- Preserve Access before every RTT `/api/*` route. The shared identity service does not relax Access or infer that OAuth callbacks will pass the deployed policy. No visual redesign, stylesheet or asset work is included; functional account controls reuse existing form controls.

## Authenticated service boundary

Expose `createD1IdentityService({ db, quotaDb, registry, enabled, clock, fetchImpl, erasers, reportError }) -> { fetch, advanceDeletions }` and a thin Worker adapter. Browser sign-in flows reach the service through RTT's same-origin proxy; no product copies the identity core.

The registry is validated, copied and frozen at construction. It has at most 16 fixed callers. Each caller binds a caller ID, product ID, `production` or `preview`, one exact canonical HTTPS origin, callback/return paths, allowed actions, and its normal environment-provided HMAC credential. Duplicate caller IDs or ambiguous same-origin environment registrations are rejected. The browser never selects product/environment/origin, an eraser URL, an account ID or a provider client configuration. Provider client IDs/redirects belong to the registered origin. No signing secret reaches public config.

Products call `createIdentityClient({ binding, callerId, secret, clock })`, which signs the exact request bytes and uses a fixed service path, a five-second total deadline and no retries. HMAC-SHA256 input is version, caller ID, HTTP method, exact service path, integer timestamp, random nonce and SHA-256 of the raw body, separated by newlines. The server bounds metadata before parsing, validates signature with Web Crypto, permits at most 60 seconds of clock skew, and atomically claims a caller-scoped nonce in D1. Nonces expire after five minutes and cleanup removes at most 100 expired rows per accepted request. A repeated nonce, wrong key, method/body/path mutation, unknown caller, invalid scope or stale timestamp fails before any provider/proof action. No browser identity header is authoritative. The signed client works over a Cloudflare service binding; absent binding/credentials means unavailable. Tests use injected local fetch, never public service discovery.

Browser forwarding uses one bounded envelope: allowlisted method/path/query, exact Origin, selected cookie values, server-observed client IP and at most 4 KiB request body. The whole service envelope is at most 16 KiB with a five-second read deadline. Reject duplicate state/code parameters, malformed JSON, ambiguous cookies and oversized URLs/headers. Reconstruct callback URLs from the registry, never a caller-selected destination. Service error responses contain static codes only and never request bodies, emails, codes, cookies, tokens, keys or provider/database messages.

The only public shared ingress, Apple server notifications, verifies Apple's signed JWS, issuer/audience/age/JTI and strict payload bounds. It is distinct from RTT `/api/*` and is off unless its audience/registered ingress is configured. A product credential cannot invoke administrative maintenance or another product's eraser.

## Browser/session contract

RTT same-origin paths are `/api/auth/email/start`, `/email/verify`, `/google/start`, `/google/callback`, `/google/cancel`, `/apple/start`, `/apple/callback`, `/apple/finalize`, `/signout`, plus `/api/account`, `/api/account/delete` and `/api/account/delete/status`. Account IDs in responses come only from a verified scoped session. Deletion requests accept the session and explicit confirmation, never a target account ID.

Session cookies are host-only `__Host-eugnel_session`, HttpOnly, Secure, SameSite=Lax, Path=/, fixed 30-day maximum. The flow cookie is host-only `__Host-eugnel_flow`, HttpOnly, Secure, SameSite=None, Path=/, ten minutes, to support Apple's form POST. There is no Domain attribute, browser-readable session storage or cross-domain SSO claim. State-changing same-origin routes require exact Origin. Provider callbacks use browser-bound flow proof; Apple notifications use their independent signature. Signout revokes the scope's session, cancels its outstanding browser flow and clears relevant cookies.

All account responses are no-store. `GET /api/account` returns only opaque account ID, session authentication/expiry times and at most five masked sign-in methods. Public configuration returns enabled/available capabilities and the public Turnstile site key only. It must not advertise a provider whose required configuration is absent.

## Proofs and linking

Adapt the verified Word Camp email, Google, Apple, flow, crypto and atomic linking core into private platform modules, with original and installed hashes and an explicit adaptation record. Keep jose 6.2.12 and oauth4webapi 3.8.8 files unchanged with MIT licences and integrity checks in the private package; do not vendor them into public RTT. Existing session tests remain frozen.

- Email: normalise/validate a maximum 254-character address; unbiased six-digit code; keyed email/code hashes, ten-minute expiry enforced in SQL, five wrong attempts and bounded verification IP rate. Every code and pending flow is bound to the captured caller scope. Email start requires successful Turnstile for the registered hostname and has no account-existence-dependent response.
- Google: state, browser flow, S256 PKCE, fixed redirect and nonce; verify RS256 signature, issuer, audience, expiry and bounded subject/email claims with cached JWKS. A trusted address requires verified email and Gmail/Googlemail or Google's hosted-domain assertion; any uncertain address follows the existing extra email-proof path, not email matching alone.
- Apple: fixed Services ID/redirect, state/browser flow/nonce, RS256 issuer/audience/expiry verification; ES256 client secret valid five minutes. Missing/true private-email claims and relay domains are never auto-merged by email. Known subjects can sign in without a repeated email claim. Refresh tokens are AES-GCM encrypted with a configured 32-byte key and fresh 96-bit nonce.
- Apple's cross-site form POST does not carry the Lax session cookie. That callback only verifies/stages the scoped browser-bound proof and encrypted grant, then returns a fixed registry-derived 303 to same-origin `/api/auth/apple/finalize`. Only finalization, with the real current session cookie matching the captured starting hash (including null), can atomically link/mint after flow expiry/replay/fence checks. Failed finalization revokes or durably retains the grant for bounded cleanup. Access and cookie policy are unchanged.
- Linking: retain the Word Camp D1 transaction/CTE decision, unique provider subject and email ownership, five-method cap and clash-with-no-writes rule. Repeat fence/existing-account checks inside the transaction. A link flow records the verified starting session hash and requires that same live account/session at callback; signout or account switching cannot silently attach it elsewhere.
- Every OAuth result carries an internal claimed-flow proof into the transaction, including ordinary trusted callbacks. The transaction requires that the scoped browser-bound unexpired flow still exists; deletion/expiry/cancellation during provider exchange cannot create a new account from an abandoned proof. Pending Google email proofs retain their verified subject until one successful code consumption, then dispose of flow and code atomically.

Provider requests use fixed allowlisted endpoints, no redirects, bounded response bodies and a five-second total deadline including consumption; injected fake providers sign real local JWTs. Arbitrary caught messages are never forwarded or logged. Do not depend on a timer firing only when fetch honours AbortSignal.

## Shared mail budget

Email sending requires explicit, validated account-wide quota configuration and a shared quota D1 used by production and preview callers. There is no default allocation. Configuration names the provider account, included monthly cap (no more than 3,000), all active fixed product/environment allocations and all legacy reserved shares; their sum must stay within the included cap. An explicit inventory/configuration revision is required. Existing Word Camp shares cannot silently be copied or reused; activation needs the coordinated live allocation and either its migration to the authority or retained fixed legacy reservation.

The quota database contains keyed counters, rolling email/IP limits and reservation receipts, not plaintext addresses. Reserve global month, caller month/day, three-per-email/hour, ten-per-IP/hour and one-per-email/rolling-minute in one transaction before sending. Every counter must have a valid nonnegative integer and a remaining slot; unknown/unreadable results refuse delivery. Two requests racing for the last slot permit one send only. Scope is registry-derived.

Reservation receipts make refunds idempotent. A definite provider 4xx refunds each reserved counter once in one transaction. Success keeps the reservation and stores the usable code. 5xx, timeout, unknown send outcome or uncertain database result retains the reservation and stores no usable code. There is no automatic resend/retry. Provider account ID, sender identity and mail copy are server configuration; endpoints remain fixed. Missing quota/sender credentials disable email while independently configured Google/Apple can operate.

## Retryable identity-last deletion

Fresh proof within ten minutes is required to begin browser deletion. The shared service atomically records a deletion job and persistent account session fence before invoking any eraser. Scoped session issuance, verification and proof/link account writes refuse fenced accounts. The job stores a fixed snapshot of registered eraser identities, bounded by the registry, and per-target durable progress. It never accepts callback URLs from a request.

The job revokes each stored Apple grant (at most five) with bounded calls; `invalid_grant` is already revoked. It invokes each fixed authenticated product eraser idempotently. Each advancement performs a bounded unit of work and returns pending/success; failures retain the account and job for retry with a static phase/error code. Erasers authenticate the shared coordinator using a separate credential, fixed product/environment and a signed idempotent job/account payload; a product sign-in credential cannot erase arbitrary accounts. Tokens/addresses are not progress/error fields.

A scoped HttpOnly opaque deletion ticket allows the browser to resume the same job after the ordinary session is fenced. Its hash alone persists. A fixed maintenance principal can advance pending jobs without accepting arbitrary account IDs; no scheduler is wired by default. Missing maintenance/eraser configuration cannot report completion. The job survives browser closure; re-proving the same fenced account can reissue a deletion-only ticket without restoring application access. No new identities are attached to fenced accounts.

Only after every required eraser and Apple revocation is acknowledged does one guarded transaction remove the account's identity/email/Apple/session/proof rows and mark the receipt complete. Preserve the minimal security fence/receipt required to reject stale work, document retention and never recycle canonical IDs. Do not claim erasure of inaccessible browser copies, backups or independent provider retention.

Apple notifications use atomic single-use JTI handling. Removing one Apple method retains accounts with another verified method. An only-way removal enters the same fenced deletion coordinator, with the only-way decision repeated inside the transaction so concurrent linking cannot be lost. Failure returns retryable refusal rather than acknowledging incomplete erasure.

## Transactional RTT product data

Add an optional customer-profile D1 repository and migration with `account_profiles(account_id, profile_id, name, markdown, updated_at)` and `account_profile_fences(account_id, deletion_job, fenced_at)`. Primary keys/indexes use account ID and the existing two allowed profile IDs. Retain the 200 KiB UTF-8 limit. Every read is account-scoped; every write is a single conditional upsert requiring no local fence. The eraser atomically inserts the fence and deletes exactly that account's bounded profile rows. A write paused before SQL executes cannot resurrect content after the eraser. Do not provide an unguarded KV customer-write path.

The Worker obtains the canonical account only from shared scoped verification, then constructs an immutable request-local profile loader for profile CRUD and answer generation. It never trusts request account headers/IDs. Enabled customer mode requires a valid session for all paid provider routes as well as profiles/answers. Missing identity/product database configuration returns static 503; signed-out returns 401 before provider calls. Config/health and sign-in remain available behind Access.

The internal eraser is a distinct fixed authenticated service action, not a public account-ID-taking `/api` endpoint. Existing `/api` Access remains unchanged. Erasure signatures bind the exact product/environment, job and account; replay is harmless because the local fence is permanent for that canonical account. D1 transaction ordering, not KV timing or browser cancellation, supplies the commit fence.

No live data migration runs. Disabled mode retains existing owner-only global KV behaviour. There is no automatic first-login adoption, email-based ownership guess, account-prefixed copy or deletion of `profile:james`/`profile:wing`.

## Browser isolation and functional controls

Bootstrap mode and verified account before mounting storage-using application state. Unknown/failed account configuration does not read legacy or another account's cache. Each account receives an immutable revocable storage scope passed explicitly to settings/history/fallback code; legacy keys remain separate. No mutable global namespace can redirect an old callback's write into a newly signed-in account.

On signout, account change, deletion, expired-session response or cross-tab session-change hint: invalidate the current application generation synchronously, stop microphone/provider work, abort answer/detector/translation calls, clear rendered state and pending queues, revoke the old storage scope, and mount only the newly verified account. Cross-tab hints trigger server verification and never establish an account themselves. Preserve existing history-consent semantics, including default-off new writes from legal #9; keep old unassigned history untouched. Deletion removes only the current account's explicit cache keys after successful server erasure. Reports disclose other browser/device copies cannot be removed remotely.

Provide functional email-code/Turnstile, Google, Apple, link-method, signout, fresh reauthentication and delete/retry controls using existing form/button primitives. No CSS/layout redesign. Disabled mode exposes none of the new flow. Account controls do not save raw tokens, codes or full emails beyond the transient form state.
